# ml4paleo v2: architecture and build plan

## Context

v1 (`webapp/` Flask + three polling runner scripts + `volume/jobs.json`, plus the `ml4paleo/` library) works for one user on one box. A code review and the open issues show structural limits: no auth, heavy work in HTTP requests on one sync worker, a JSON file as the job store, stuck jobs after crashes, a random-forest-only model with no ignore label, an annotator that serves random 512² patches with no provenance or undo, and local-disk-only storage. v2 is a ground-up re-architecture on branch `v2` (created from `master` at `e97ceab`, after #74–#76 merged). Goals: accounts and sharing, one annotation app (brush, polygon, auto-annotation) with provenance that scales from small training cubes to hand-annotating a whole volume, swappable neural-net segmentation, a real job system that can offload to other machines or the cloud, and storage that works on local disk, S3, or GCS.

| Database | Postgres only: app data, op log, and the job queue. No Redis. Alembic migrations. |

| Sharing | Owner + collaborators, full access, no role tiers. |
| Project | One volume per project (optionally multichannel), multi-class label set. |
| Quotas | User-facing limits are plain: **storage** (default 10 GB) and **trained models** (count of models a user keeps; deleting one frees a slot). Every dimension (also optional CPU-hours, GPU-hours) is independently configurable per deploy; unset = unlimited. Unlimited projects within quota. "Request more" button → short form → email (or admin inbox when no SMTP). |

| Compute | One worker image (CPU and CUDA variants), three ways to run it: local containers (GPU worker auto-enabled when a GPU is detected), remote pull workers (outbound HTTPS only), SkyPilot burst (AWS/GCP/K8s/SSH, scale to zero). |

## Architecture

### Core invariants
1. **Projects have no status enum.** State is derived from committed artifact heads and active pipelines, so the web app and workers can never overwrite each other's status (in v1, saving an annotation could cancel a queued training run, and a retrain could hide finished downloads).
2. **Committed artifacts are immutable.** Each lives at `projects/<pid>/artifacts/<aid>/`; "current" is a DB pointer (`artifact_heads`). Commit is one DB transaction after the worker writes `_MANIFEST.json` last. Partial outputs never become "latest"; export caches keyed by source artifact can't go stale (v1 could cache a partial segmentation zip forever).
3. **One axis boundary.** Storage is `c,z,y,x`. The only XYZ↔ZYX transpose is in `ml4paleo/ome.py`, covered by golden tests (v1 shipped both a transposed PNG export and mirrored meshes).
4. **Heavy work never runs in a request.** The API only enqueues, streams bytes, or applies small label ops.

Library extras keep the server light: the base install (numpy, zarr≥3, obstore, pydantic, pillow, zstandard) is all the API server gets; `[dicom]`, `[rf]`, `[mesh]`, and later `[torch]` are for workers, and `[v1]` holds the old Flask app's dependencies until it is deleted. `requirements.txt`, intern, and the `numcodecs<0.16` pin are gone.

Reused from v1: `_extract_zip_archive`, `_should_ignore_source_file`, `_get_volume_provider` (`webapp/conversionrunner.py`) → `handlers/ingest.py`; `DicomVolumeProvider` spacing logic; `ChunkedMesher` axis/winding fix and `mesh_info.json` (`ml4paleo/meshing/__init__.py`); `_default_features_func` (`ml4paleo/segmentation/rf.py`); `_foreground_metrics` (`webapp/segmentrunner.py`) for per-class metrics; `normalize_annotation_volume` windowing (without the 8-bit cast); v1 sample metadata helpers `get_annotation_pairs`, `load_annotation_sample_metadata`, `annotation_sample_metadata_for_z` (`webapp/apputils.py`) for the importer; bossypaints' viewport loader (`ImageCache.ts`, `getViewportChunkWindow`, `getVisibleChunksForWindow`, progressive levels, `cancelRequestsExcept`) and propagation registry (`server/bossypaints/propagation.py`), both Apache-2.0.

### Data model (Postgres, UUIDv7 keys)
- Identity: `users` (status, is_admin, quota_override jsonb), `sessions` (hashed token), `oidc_providers`, `oidc_identities`, `auth_tokens` (verify/reset/invite), `rate_limits` (unlogged), `site_settings`, `quota_requests`.
- Projects: `projects` (owner, `v1_job_id` unique), `project_members`, `volumes` (shape_czyx, dtype, voxel_size_zyx), `channels` (window), `label_sets`, `label_classes` (0 = unlabeled, 1 = background, 2–254 classes, never reused).
- Labels: `label_chunk(layer, cz, cy, cx, version, class_sha, source_sha, n_labeled, class_counts)`, `op(op_id, op_seq, user/worker, client_op_id, kind, source, tool_params, model_id, job_id, bbox, reverts, conflicts)`, `op_chunk(op_id, chunk, base_version, new_version, new_sha, claim)`, `roi(bbox, kind, status open|complete|skipped, split train|val, origin, score)`, `roi_suggestion`, `training_set(id = sha256 manifest)`, `model` (plugin, version, params, training_set_id, parent, class_map, metrics, artifact).
- Artifacts: `artifacts(kind, state staging|committed|superseded|failed|deleted, bytes, inputs, manifest, produced_by_job, head_slot, cache_key, expires_at, state_changed_at)` (files at `projects/<pid>/artifacts/<aid>/`, derived from the ids), `artifact_heads(project_id, slot, artifact_id)`, `jobs.grants` (`[{path, access}]` under `projects/`), `uploads` (S3 multipart, step 10).
- Queue: `jobs(root_id, parent_id, kind, tier, status blocked|queued|leased|succeeded|failed|cancelled, payload, required_labels[], min_vram_gb, weight, attempts, lease_worker_id, lease_token, lease_expires_at, progress, idempotency_key, scale_trigger bool)`, `job_deps`, `job_attempts`, `workers(token_hash, pool local|remote|burst, labels[], vram_gb, slots, status, last_seen)`, `burst_nodes`.
- Accounting: `usage_ledger`, `user_usage(storage_bytes, trained_models)`, `audit_log` (which also records v1 claims and releases; a claimed job is its project's `v1_job_id`), `email_outbox`.

### Worker protocol (`/api/worker/v1`, `Bearer m4pw_<random>`, server stores sha256)
`POST /hello` · `POST /claim` (long-poll ≤25 s, woken by LISTEN/NOTIFY with a 5 s poll as backup; returns job + StorageGrants) · `POST /jobs/{id}/heartbeat` (30 s; 120 s lease; carries progress; returns cancel flag, refreshed grants) · `POST /jobs/{id}/complete` (idempotent) · `POST /jobs/{id}/fail` (`retryable` or not) · `POST /jobs/{id}/release` (a stopping worker hands a job back without using an attempt) · proxy object endpoints for workers without direct storage credentials (step 9). Messages live in `ml4paleo/protocol.py`, shared by server and worker. Every claim carries the worker's caps (kinds, labels, VRAM), so processes that share a token (replicas, or the CPU and GPU workers on one box) can differ; the worker row keeps the last caps seen, and "online" is derived from `last_seen_at`. Every state change is conditional on the lease token (stored hashed); stale leases get 409 and discard output. The housekeeper reaper requeues expired leases with backoff (30 s doubling, max 3 attempts), then fails the job and cancels the rest of its pipeline; it also queues any blocked job whose dependencies all succeeded, as a safety net. Claim query: `FOR UPDATE SKIP LOCKED`, filtered by `kind = ANY(caps.kinds)`, `required_labels <@ caps.labels`, and VRAM, ordered by tier then pipeline submission time (FIFO). Dependencies stay within one pipeline. When parents finish together, each locks the waiting children before checking them, so the last parent to commit always releases the child. A pipeline is cancelled by setting its root job's flag: `cancel_pipeline` waits only for the root row and skips busy rows, and claims, reports, heartbeats, and the reaper all honor the root's flag, so nothing slips through. Locks follow one order (the job, then its pipeline root, then waiting children; workers last) and use `FOR NO KEY UPDATE`, which foreign-key checks don't block. `enqueue` re-reads dependencies under a share lock. Admin API: worker tokens (`/api/admin/workers`), the job list, cancel, and a `noop` diagnostic job; `ml4paleo-server check-workers` runs one from the command line.

### Pipelines (DAG in `jobs` + `job_deps`, progress = Σ weight·progress over `root_id`, SSE to the browser)
- **Upload:** S3 multipart straight from the browser (`/api/projects/<id>/uploads`): the declared size is reserved against the owner's quota at start; the API presigns part URLs (1 h, path-style, signing the part's exact `Content-Length`, so storage refuses a wrong-sized part); to resume, the browser asks which parts storage has (upload id in IndexedDB) and sends the rest; the API completes only when every part is stored with the expected size (64 MiB parts, more for files over 625 GiB; 5 TiB max). Completion commits a `completing` state before asking storage to assemble the parts, so a retry after a crash at any point converges (an assembled file of the right size is accepted; parts still there are assembled), and cleanup of an abandoned `completing` upload both aborts the multipart upload and deletes any assembled file. Unfinished uploads are aborted after 7 days and finished ones deleted after 30 unless a job uses them; jobs can only be given finished uploads. Needs S3-compatible storage (501 on `file://`). On a single box Caddy passes only signed part PUTs (`/ml4paleo/projects/*` with `uploadId`, `partNumber`, `X-Amz-Signature`, and no copy headers) to SeaweedFS on the app's own origin, so no CORS, and strips every `x-amz-*` request header, since the signature covers only the host and length (an unsigned `x-amz-copy-source` would turn a part upload into a copy of another project's file). The compose smoke test uploads a real file this way and checks that a short part is refused and that a copy attempt never reaches storage.
- **Ingest:** `POST /api/projects/<id>/ingest {upload_id}` (a finished upload: one zip of 2D image slices, ordered by name with numbers compared as numbers, or of a DICOM series, ordered along the slice normal; files that aren't slices — notes, manifests, a DICOMDIR, DICOM files without an image — are skipped and named in the image manifest as `skipped` and `skipped_count`, a few files of an unknown kind are skipped too but more than five are refused, and an archive with several DICOM series uses the one with the most slices and says so in the manifest's `notes`) creates the image artifact (staging, head slot `image`) and `ingest.probe`. Archives are read in place through range requests (`open_object`, a seekable buffered reader over the storage grant), member by member, so nothing downloads or unpacks the whole file. Archive guards: the entry count is read from the end-of-directory record (ZIP64 too) before the directory itself, and more than 200k entries are refused; unsafe member names refused (even skipped ones); only stored and deflate members (Python doesn't bound bzip2/LZMA output) and no encrypted ones; total expansion over 1000× refused; members are read in 1 MiB chunks, so deflate output stays within the declared size (a member that claims less than it holds fails as damaged). Each job has a memory budget (the worker's memory, from its container's cgroup limit when it has one, times 0.75, shared among its slots), and a slice's archive member and its decoded pixels may each take a quarter of it (64 MiB to 2 GiB), checked from the image or DICOM header before decoding; compose caps the workers' memory (`M4P_CPU_WORKER_MEMORY`, default 4g) as the last line. A single multi-frame DICOM works too. Damaged archives, bad slices, and malformed probe results (checked before the success is recorded) fail for good. The probe creates the empty OME-Zarr image and writes the slice order to `ingest/source.json`; when it succeeds, the server (`pipelines.after_success`, in the same transaction as the success) adds one `ingest.slab` per shard-deep slab (parallel), one `pyramid.level` per level, and `artifact.finalize`, which records a histogram and default window (0.5–99.5th percentiles of the coarsest level), removes the index, and writes the manifest; its success commits the artifact as the project's image (`GET /api/projects/<id>/image`). Problems with the upload are permanent failures whose first line is shown to the user. Pipelines: `GET /api/projects/<id>/pipelines[/<id>]`, `…/cancel`, and `…/events` (server-sent `status` events, at most once a second, ending when the pipeline finishes or the viewer's sign-in or membership ends; 204 for a pipeline that has already finished, which stops EventSource reconnecting). Staging artifacts that a waiting or running job has a grant for are never abandoned. The compose smoke test ingests a small stack with the real worker.
- **Train + predict:** `training_set` manifest (REPEATABLE READ snapshot: image id, label `op_seq`, ROIs, free labeled regions, chunk shas) → `train` (plugin caps choose CPU/GPU) → `predict.shard` fan-out (512³ shards + halo, outputs classes + uncertainty + 64³ uncertainty grid) → pyramid → finalize → `suggest_rois`. `predict.region` (ROI-scoped, high tier) feeds the proposal overlay.
- **Final segmentation:** `compose_final` per shard = prediction → per-class dust removal (`cc_block` → `cc_merge` union-find → `cc_apply`) → human-label override (`where(label≠0, label, pred)`, complete-ROI unlabeled = background).
- **Mesh:** `mesh.block` (1-voxel overlap; downsample mode/max/gaussian, #22/#24) → `mesh.merge` per class (STL/OBJ/GLB + Neuroglancer precomputed).
- **Export:** zarr-zip, TIFF/PNG stack (in upload orientation), mesh bundle; cached by `(source_aid, fmt, params)`, 7-day expiry, presigned GET.
- **Label import:** labels made elsewhere, from an upload the size of the image: a TIFF with a page per slice, or a zip of TIFF or PNG slices in name order (ordered as ingest orders a scan's; rows y, columns x). `POST /api/projects/<id>/labels/imports {upload_id}` starts a check (`labels.probe`, "label check"; asking again for the same upload gives its first check), which fails for good, giving both sizes in x × y × z, unless the file is the image's size (from the number of slices and the first one's header, before reading the rest), then reads every slice once, refusing other image formats (lossy ones would change the numbers), slices with more than one channel, values that aren't whole numbers (32-bit floats holding whole numbers are fine), and more than 253 values besides 0 (more than a project has class values), and counts each value's voxels. A TIFF is copied to the worker's disk first, since Pillow decodes a compressed page of anything else by reading the whole file. The person then says what each value becomes, background, a class, or a new class (named and colored in the request, and made then), and values left out stay unlabeled: `POST …/labels/imports/<check>/start {mapping, overwrite}`, once per check, and refused if the image's size changed since, starts `labels.import` ("label import"). It reads the slices a chunk deep (in bands of chunk rows if a chunk-deep slab of label values wouldn't fit in a quarter of the job's memory, reading the slices again for each band), maps them through a lookup, and sends each 64³ chunk that labels anything as one edit through the worker's label-op endpoint, named by the upload and chunk (`uuid5`), so a retried job sends each chunk once; network or server errors on one edit are retried for two minutes before the job fails and is tried again. Its edits are `Source.IMPORTED` and the starter's (`user_id`), with `tool {name: "label-import", import, file}` saying where they came from, and fill only voxels nobody labeled unless `overwrite`. The upload counts against the owner's storage like any other; the check cuts its life to two days, and starting the import to now, so garbage collection deletes it once no job uses it, however the import ends. `DELETE …/labels/imports/<check>` stops whatever of it runs and lets the file go (labels already in stay). `GET …/labels/imports[/<check>]` gives each import's state (checking, ready, importing, done, failed, cancelled, or expired: checked, but the file is gone), the pipeline to follow, the size and values found, and the lookup used; the jobs hold all of it, so there's no table.
- **v1 import:** up to three pipelines (the image, then the labels and the prediction, each on its own) whose `v1.*` jobs run on a worker labelled `v1-volume` (v1 volume mounted read-only), which runs nothing else; the image's pyramid and finalize jobs run on any worker.

### Label edit path
- Client rasterizes every committed action into per-chunk bit-packed mask deltas (geometry kept in `tool_params` for audit); one op = one stroke/polygon/fill/accept. Ops queue in IndexedDB, flush within 250 ms, retried idempotently by `client_op_id`. Status chip: Saved / Saving n / Offline n (no connection) / Can't save right now n (the server answered with an error, so edits wait and try again).
- Server writer (one transaction per op): idempotency check → lock chunk rows in sorted order → rebase on stale `base_version` (strict ops 409 on overlap; brush ops last-writer-wins per voxel) → write new content-addressed blobs `labels/{layer}/blobs/{sha}` → log `op` + `op_chunk` → NOTIFY (collaborators refetch via ETag). Zoomed-out display levels aren't written here: they follow from the new chunk versions when a viewer asks for them (see "Built (label pyramid, server)").
- Each applied delta records a **claim**: the voxels the op actually wrote (after `only_if`) and the values it wrote there. A chunk's labels are always the overlay of every live op's claim in op order (each voxel takes the value of the last live claim covering it, else unlabeled). Undo and redo are new ops (`reverts=op_id`) that flip an op between live and undone and recompute only that op's voxels from the remaining live claims, so the result never depends on the order of undos and never disturbs voxels a later op also wrote. A property test checks that incremental state always equals a full overlay. Workers (propagation, interactive, imports) submit ops through the same writer with a worker token.
- Everything decoded from a client (masks, values) is decompressed with a hard output limit equal to what its box allows. Label chunks are fixed at 64³ uint8 (sparse and highly compressible); the step 14 viewer spike only decides image chunk sizes.
- Built (step 13): tables `label_classes` (2–254, values never reused, retired with `deleted_at`), `label_chunks` (version, class and source blob hashes, labeled-voxel counts per class), `label_ops` (`seq`, `client_op_id` unique per project, kind edit/undo/redo, `live`, tool, bbox, target), `label_op_chunks` (versions before/after and, for edits, the claim box/mask/values), `rois`. API under `/api/projects/<id>/labels`: classes; `POST ops` (base64 masks; values must be 0, 1, or a live class; one delta per chunk, up to 512; `strict` refuses with the changed chunks); `ops/<seq>/undo|redo` (409 if already in that state); `ops` history; `changes?after=` and `events?after=` (SSE `change` events, while the viewer stays signed in and a member; a reconnect resumes after `Last-Event-ID`) — ops take their `seq` under a per-project lock held until commit, so seqs commit in order and paging by seq never skips one, and a retry that races its first attempt waits for it and gets its result; and `zarr/` — a zarr group with `class` and `source` uint8 arrays shaped like the image in 64³ chunks, served from the current blob with `ETag` = content hash, `If-None-Match` → 304, `X-Chunk-Version` (the next edit's `base_version`), and 404 for all-zero chunks. ROIs under `/api/projects/<id>/rois` (cube or one-voxel slice inside the image; status open/complete/skipped; split train/val). Blobs live at `projects/<id>/labels/blobs/`; reading needs a project image (409 before ingest). Still to come: garbage collection of unreferenced blobs.
- Built (label pyramid, server): the label zarr also has `class_1`, `class_2`, … for the image's pyramid levels (`class` is level 0), so a zoomed-out view can show labels without fetching every full-resolution chunk. Each array has its level's shape and 64³ chunks, and a voxel at level k covers the same block of the volume as the image's. The manifest records no per-level shapes, so the server plans the levels as ingest did (`ml4paleo.ome.plan_levels` from the manifest's shape and voxel size, for the 64³ chunks every image has; an image whose `levels` doesn't match the plan has level 0 only), and the group's `ml4paleo.label_levels` lists each array's name, shape, and `factor_zyx` (full-resolution voxels per voxel along each axis, as the viewer reads them from the image). The levels are display only: derived, never written by an edit, never read by training, exports, accepts, or segmentation. A level shrinks the one below it block by block (`ml4paleo.labels.pyramid.downsample_labels`; a block is two voxels along each axis the image halves, one along the others): the block's most common class (value 2 or more, the lowest value among classes that tie), else background if any voxel is, else unlabeled. A class beats background however few voxels it has, so a one-voxel line survives every level, and classes never mix. A retired class still has its voxels in the chunks, but the viewer draws them as nothing, so the pyramid counts them as unlabeled and they can't outvote a class that shows; a chunk that shows nothing for that reason is made once like any other and kept as an empty chunk (a 404 to the viewer), so a big region of retired classes doesn't start over on every request. Chunks are made when asked for (`label_pyramid.py`; no tables, no migration): level 1 from the stored full-resolution blobs, level k from the chunks of level k − 1 under it, each kept as the bytes a viewer gets in a per-process least-recently-used cache (`M4P_LABEL_CACHE_MB`, 64). One query over the `label_chunks` rows under a chunk says which state of the labels it shows: how many of them have labels, and the sum of their versions, which goes up with every edit, undo, or redo of any of them (for the top chunk that is a pass over every label row of the project, 15 ms at 500,000 rows with no class retired, 22 with one, 26 with five, and 38 with sixteen, the most it tests for, on every revalidation). The sum is the chunk's `X-Pyramid-Version` (not `X-Chunk-Version`, which the viewer takes as the version an edit builds on); its ETag adds the image's id and the shape and factors of every level (a replaced image, or a change to how levels are planned, can change the pixels, labels unchanged), the retired classes, but only for a chunk that has voxels of any of them (the same query tests each chunk's voxel counts per class, once for all the classes, for up to 16 retired, past which every chunk follows them), and a rule version that is bumped whenever the rule or the codec changes (a test pins both); and the same state keys the cache. So, with no more than 16 classes retired, retiring a class changes the ETags of the chunks that have retired voxels (of it, or of an earlier retired class, whose pixels may then be the same) and of no others, and retiring one nothing was painted with changes no chunk that has no retired voxels; past 16 it changes every chunk's. An ETag is only unique to its URL (two chunks can have the same one), so nothing may tell chunks apart by it. A revalidation costs that one query, an edit costs one new chunk per level (made from one new chunk and cached ones), and a chunk with no labeled chunk under it is a 404, as at level 0. The first request for a chunk high up may have to build everything under it, so the work is shared and bounded. One request at a time builds a chunk (others wait for it). Reading the chunks under a chunk of level 1 and shrinking them, and combining chunks of higher levels, each take one of two slots per process (never held while waiting for another chunk, so they can't deadlock), and a request that would queue behind eight others is turned away at once, as is one that has waited for a slot, or for other requests' builds, until a few seconds after its own time is up; no request holds a database connection while it waits, for another request or for storage. A request works for 1.5 s or until it has read 512 stored chunks, finishes the chunk it is on, and answers 503 with `Retry-After` (1 or 2 s, by chunk), having kept what it made: the chunks it finished stay pinned (exempt from the cache's limit, up to 16 MB or the cache's size, whichever is more) until the chunk above them is made, or two minutes pass. A client must ask again, with jitter of its own: zarr readers take a 503 for an error and show nothing. The 503, like every answer for a coarse chunk, has `X-Pyramid-Version` and `Cache-Control: private, no-cache`. A chunk that stands for 64 or more labeled chunks is also kept in the project's storage (`labels/pyramid/<level>/<z>/<y>/<x>`, one object per chunk, headed by the state it shows and used only for that), so processes and restarts share what took long to make; it is a cache, made again if it can't be read or written, and safe to delete. A build doesn't store its chunk over one it found kept, for the same plan, for a newer state. It can't tell one stored since it looked, or one made for other retired classes, which an older build can still replace; the next build for a newer state replaces that in turn, and no pixels are wrong either way, as a stored chunk is only used for the state it says (a conditional write would close the first case, but not every store has one). Nothing deletes these objects (deleting a project is soft, as for label blobs), so the garbage collection that is to remove unreferenced blobs has to cover `labels/pyramid/` too. Measured on a laptop with a real server, for a fully labeled 1024³ volume of random labels (eight classes among background and unlabeled, the worst case, since nothing is uniform and nothing compresses; 4096 chunks, about 4700 chunks shrunk to make the whole pyramid), the cold top chunk took 8 requests of at most 1.4 s (512 stored chunks each), 11 s of work in all, and the process grew by 64 to 78 MB (its cache, full). Four worker processes took the same however the requests were spread over them, even when each went to one of four separate processes at random (which took 18 to 29 requests before chunks were kept in storage), and after a restart the top chunk is one request of 50 ms. Once made, a chunk comes in about 6 ms, a revalidation in 5, and an edit to one chunk makes the top chunk again in 80 to 130 ms. Known limits, all bounded: a chunk found in storage doesn't let go of what an earlier request that gave up pinned under it (until its two minutes are up); a request that waited for another's build doesn't pin the chunk it got, for its own retries; a request cancelled while it combines chunks gives its slot back while the thread finishes; and a chunk kept in storage is read whole (up to 256 KB) before its header is compared, which is one round trip for a hit, the case that matters, and a wasted download only when it is for another state.

- Built (step 16, edits stay shown): once the server answers, a copy of the chunk read just before the op (a load that started before the edit) gets the edit put back and counts as the version the op made, so it takes no second load; a copy from before someone else's change as well, or of a version not known, gets it put back too and the chunk loads once more, for as long as such a load runs; and a copy newer than the op (read after later changes, with the edit put back over them) says the op's version, which the server is past, until the chunk loads again. - Built (step 18, final segmentation): `POST /api/projects/<id>/segmentation {min_voxels}` composes the current prediction into a "segmentation" head: `compose.prepare` → `cc.block` per shard → `cc.merge` → `cc.apply` per shard → `compose.finalize` (`ml4paleo.segmentation.compose`). Each voxel takes its label if anyone labeled it (including accepted predictions), else background inside a complete ROI, else the prediction; then each class's 6-connected pieces smaller than `min_voxels` become background unless someone labeled part of them. Pieces are counted across shards: `cc.block` decides the pieces that touch no seam (a face shared with another shard) itself, and passes on only the seam pieces, numbered compactly, with their sizes capped at `min_voxels` (a labeled piece counts as `min_voxels`), their classes, and their numbers on the seams; `cc.merge` reads those summaries one at a time and joins same-class seam pieces touching across seams as connected components of a sparse graph (scipy) with one edge per pair of pieces, so its memory follows the seams rather than the number of specks; `cc.apply` relabels (labeling is deterministic) and writes the shard. A shard job holds the shard and one int32 array of piece ids, reused for each class, and counts by z slabs sized from its memory budget; every step works out what it needs first and fails for good with a clear message rather than go over its budget. Labels and complete ROIs are pinned at start (chunk hashes, carried in `compose.prepare`'s payload, which writes them into the artifact as `inputs.json`, so a start that never commits leaves no files), so later edits don't change the result; per-shard scratch files (compressed `.npz`) are deleted at the end, and the scratch of a failed or cancelled run goes later, when garbage collection removes its failed artifact. A project makes one at a time (409 with the running pipeline's id), and only from a prediction of its current image. `GET /api/projects/<id>/segmentation` describes it from what the server recorded at start (model, `min_voxels`, and `labels_as_of`, when the newest included label edit was made); the annotator shows it as a layer, and the new Results page makes it and follows the newest one from the project's pipelines, so it survives a reload.
- Built (step 18, meshes): `POST /api/projects/<id>/meshes {downsample 1|2|4|8, method any|majority, simplify}` meshes the final segmentation into a "meshes" head: one `mesh.block` per 256³ block → a `noop` that waits for them all (so joins depend on one job, not every block) → one `mesh.join` per class → `mesh.finalize` (`ml4paleo.meshing.blocks`). Each block reads one extra coarse voxel on its high sides, so neighbouring blocks produce the same vertices on the plane they share, and pads with nothing at the volume's faces, so surfaces there are closed. zmesh takes memory and time in proportion to a surface (a porous block can take gigabytes and minutes) and holds the GIL throughout, so a block counts its class/non-class voxel faces first and meshes in sub-boxes, halved on a power-of-two grid until each fits half the job's memory budget and about 20 s of zmesh; sub-boxes meet the way blocks do, and a block too detailed even in 16³ sub-boxes fails for good, asking for a coarser resolution. Blocks write each class's pieces, seam vertices marked, to `scratch/<block>/<value>.npz` as they go, and a summary to `scratch/<block>.json`. A join streams its class block by block: it welds seam vertices through a dict (dropping each block's once no later block can reach them) and drops triangles that collapse, writes the STL as it goes, spools vertices and triangles to disk for the OBJ and GLB, and uploads from disk (the storage proxy gets a streamed PUT; obstore's HTTP store would hold the file in memory), so its memory doesn't grow with the mesh. A file over the proxy's 4 GiB, or more seam vertices than the budget holds, fails for good, asking for a coarser resolution or more simplification. Each join writes `<value>.json` (triangles, vertices, files) for finalize. Downsampling (#22/#24) keeps a coarse voxel if any of its voxels is the class (thin parts survive) or if most of those inside the scan are (smoother); coarse voxels cut by the scan's far faces end at them. `simplify` bounds how far simplification may move a surface, in voxels at that resolution (0 keeps every triangle); vertices on seams never move, so simplified pieces still join. Meshes are in (x, y, z), scaled by the voxel size of the image the segmentation was predicted from and in its unit (voxels if the scan gave none), as `<value>.stl`, `.obj` (nine significant digits), and `.glb` (the same vertices, with the node scaled to meters, as glTF expects), with `mesh_info.json` (axis order, units, voxel size, options, and per class its name, color, files, and counts). A project makes one set of meshes at a time (409), and not while its owner is out of storage (403). The v1 `ChunkedMesher` moved to `ml4paleo.meshing.chunked`, imported lazily so the package stays importable without the mesh extra. `GET /api/projects/<id>/meshes` gives the info, the source segmentation, and a `files_url` under `/api/projects/<id>/artifacts/<artifact>/files/` (the data gateway, for downloads); the Results page makes meshes, follows running pipelines after a reload, flags meshes made from an older segmentation, and links each class's files, named for the project, the class's value, and its name (letters in any script).
- Built (step 18, exports): `POST /api/projects/<id>/exports {source: image|prediction|segmentation|meshes, format: zarr|tiff|png|zip}` makes one zip archive of a head artifact as an "export" artifact: `export.files` puts every file of a volume's zarr group at the archive's root (so `zarr.storage.ZipStore` opens it; an image comes out as OME-Zarr) or the meshes in a folder named by class with a matching `mesh_info.json`, and `export.images` writes one TIFF (zlib; any image type) or PNG (8- or 16-bit unsigned) per z and channel, y down the rows as the stack was uploaded, reading a chunk's depth of slices at a time within the job's memory budget (`ml4paleo.export`). Archives are written as numbered parts of 64 MiB (`parts/00000`, …), so every backend takes them in single requests, the storage proxy included, with fixed entry dates so a retried job writes the same bytes; the manifest lists the parts' sizes. `GET …/exports/<export>/download` serves the parts back to back as one file with byte ranges (resumable downloads) and its filename, through the API rather than presigned storage URLs, so the single-box deploy exposes nothing new. The cache key is (source artifact, format, archive layout): asking again for an export that is kept or still being made gives that one and keeps it another week; exports otherwise expire after 7 days, count against the owner's storage until garbage collection deletes them, and `DELETE …/exports/<export>` stops one or lets it go. Starting a download keeps the export at least six more hours, and garbage collection waits 30 minutes past an expiry, so running downloads finish. An export is refused up front when its source (its size, roughly) wouldn't fit in the owner's remaining storage, and PNG only for 8- or 16-bit unsigned images. Entries streamed from storage use data descriptors, which some streaming readers (Java's `ZipInputStream`) refuse for stored entries; ordinary unzip tools and zarr read them. The Results page lists the downloads with progress and lets people make, download, and delete them, flagging ones made from an older source.
- Built (step 19, v1 import): `POST /api/v1-jobs/<id>/claim` imports a v1 job into a new project of the caller's (`projects.v1_job_id`, unique) and returns the pipelines it started (`pipeline_ids`). The SPA's `/job/[...path]` takes v1's old links (`/job/<id>`, `/job/<id>/{annotations,models,download}`, `/job/annotate/<id>`, `/job/annotate-v2/<id>`) and imports the job when a signed-in visitor confirms; `/import` lists the jobs this browser opened in v1 (`localStorage["jobs"]`, so v2 must be served from v1's exact origin: the same scheme, host, and port), which can include other people's shared jobs, and takes pasted ids or links, importing one at a time. The first claim wins (per-job advisory lock); a deleted project lets go of its job; jobs whose upload never converted (pending, uploading, uploaded, converting, or convert_error, as v1's job page has it) are refused. Ids are six hex digits and an address can sign up five accounts an hour, so each account and each address may try `M4P_V1__CLAIMS_PER_HOUR` claims an hour (default 30), of which `M4P_V1__MISSES_PER_HOUR` (default 5) may be ids that aren't jobs, and once `M4P_V1__SITE_MISSES_PER_HOUR` (default 200) misses have come in from anyone, nobody can claim until the hour is up. The site-wide stop is checked first and then each one's misses, so a refused claim counts against nothing else; a claim counts as a miss (one conditional UPDATE each) before `jobs.json` is read and is given back if the job is there, so guesses made at once can't get past the limits. Each miss is audited (`v1.claim.miss`). `POST /api/v1-jobs/<id>/release {to}` lets an admin give a job to the account it belongs to: a project someone else made from it is stopped and deleted as deleting it would (its pipelines cancelled, its models' slots given back), and only that account can claim the job next; giving it again undoes a mistake, and a job nobody has claimed can be given too. Claims and releases are audit events against the job (target "v1_job", the job id, which `ix_audit_log_target` indexes), and a claim looks at the last of them. The API reads only v1's `jobs.json` (`M4P_V1__VOLUME_PATH`; `deploy/compose/compose.v1.yml` mounts just that file, read-only, and since v1 saves it by replacing it, the API needs a restart to see what v1 changes after it starts). The import runs on a worker started with `--v1-volume` (label `v1-volume`), which then runs only `v1.*` jobs; compose gives it an internal network (no internet) that only Caddy shares. It is up to three pipelines (`ml4paleo.v1import`): `v1.probe` → `v1.slab` per shard-deep slab (v1's zarr v2 `(x, y, z)` array through `ZarrVolumeProvider` and `write_from_provider`, reading a few source chunks at a time, sized from the job's memory) → pyramid → `artifact.finalize`; once the image is in, `v1.labels` and `v1.prediction` each start as a pipeline of their own ("import labels", "import prediction"), so one failing doesn't stop the other. Before any slab runs, the server refuses an import that won't fit in the owner's storage: its image (voxels × item size × 1.15 for the pyramid) and prediction (a byte a voxel), beside what the owner's other imports still running will add. A part is done when a job of it has succeeded, and claiming the job again opens the project and starts whichever parts aren't done or running: the whole import if the image never came in; otherwise, if the import's image is still the project's, the labels, and the prediction unless the project has one since (from a model of its own) or it won't fit (its failed pipeline says why). Every part can run again: the image is made anew; the labels' edits are named by v1 job and sample (so ones that landed aren't applied twice), only fill voxels nobody has labeled when brought over again (so edits made since stay), and add their ROIs once; and a new prediction replaces the one before. Releasing or deleting the project stops the labels and prediction even if the image's finalize starts them meanwhile: it share-locks the image pipeline's root, which stopping the project (`train.stop_project`, pipelines before the project) cancels before looking again for pipelines started since. Voxel sizes come over where v1 recorded them, which it did only for DICOM scans converted from #76 on; other jobs import in voxels. v1 had one class, so the import adds "Foreground"; each annotation sample whose metadata places it (v1 from April 2026 on; metadata with impossible numbers counts as unplaceable) becomes one label edit, sent through the label writer by a lease-checked worker endpoint (`POST /api/worker/v1/jobs/<job>/label-ops`, only for kinds that write labels, refused once the job is cancelled), writing Foreground where the mask's red channel is above 0 and background elsewhere inside the cutout (padding excluded), plus a complete slice ROI (origin "v1"). Older samples can't be placed and are counted as skipped. The newest segmentation known to be finished becomes the prediction (any nonzero value → Foreground, 0 → background): one named by a sidecar v1's segment runner wrote (with `training_samples` or `metrics`, and without `legacy_metadata_migrated_at`, since v1's "migrate metadata" button names a segmentation whenever its folder exists), else the newest one when the job's status says segmenting finished; only names like v1's (`[0-9]+.zarr`) count, and it's read a source chunk deep, so each chunk is decoded once. v1's models aren't brought over (2D features and scikit-learn pickles; their segmentation is), nor its meshes (make them again from the final segmentation). `webapp/` stays until a dry run against a copy of the production volume.
- Built (history): `GET /api/projects/<id>/labels/ops` (newest first, `limit` at a time between ops `after` and `before`) says who made each op (`username`; for edits a job made, such as a v1 import's, `job_kind`), where accepted labels came from (`accepted`: a prediction or a proposal, by the artifact's head slot, with the model's id and name, the v1 job for a prediction brought over from v1, and the ROI, none for labels accepted in a view), and for an undo or redo, its edit as that is now (`target`), with one query per kind of name however many ops; `user_id` and `source` filter it (an undo or redo has its edit's source). Each edit has Undo or Redo (a fresh `client_op_id` per click; a 409 says it's already that way, and the list catches up), and so does the newest undo or redo of an edit while it still holds. - Plugin label space: background 0, classes 1..K, IGNORE 255 (from unlabeled voxels outside complete ROIs).
- RF: labeled voxels only, balanced per-class sampling (replaces the 1/500 negative stride), 3D features, halo = round(4·σmax) + 2.
- nnU-Net v2: crops as cases, `ignore` label in `dataset.json`, pre-normalized `noNorm` channel with a global window, time-budgeted trainer, warm start from parent model.
- MONAI SegResNet: CE with `ignore_index` + masked Dice, label-balanced patch sampling, sliding-window inference.
- Metrics: per-class Dice/IoU on validation ROIs (20% of non-suggested ROIs once ≥5 exist), not on training data.
- Active learning: score 64³ cells by top-10% entropy (from the uncertainty grid, or sampled crops inside the specimen mask), NMS + diversity, 20% random exploration.

### Scheduling, compute, and burst
- Local workers via compose; `setup.sh` detects `nvidia-smi` and the NVIDIA container runtime and sets `COMPOSE_PROFILES=gpu`. Local workers share one token (`secrets/worker_token`, registered by `migrate`) and reach only the worker API, through an unpublished Caddy port on the `jobs` network.
- Remote workers: admin creates a worker token in `/admin/workers`, runs `docker run ghcr.io/j6k4m8/ml4paleo-worker-gpu --server ... --token-file ...`.
- Scaler (compose profile `burst`, sole holder of cloud credentials, runs the SkyPilot API server with Postgres state): every 30 s, per pool: demand = queued `scale_trigger` jobs whose requirements match the pool and no non-burst worker can take soon → target nodes = clamp(ceil(backlog/30 min), `min_nodes`, `max_nodes`) → `sky.launch` worker clusters (`down=True`, idle autostop, per-node expiring worker token) → reconcile and tear down idle/orphaned/silent nodes. Background-tier jobs set `scale_trigger=false`.
- Pool config example: `pools: {train: {node_type: L4, max_nodes: 2}, predict: {node_type: L4, max_nodes: 4}, interactive: {node_type: A10G, max_nodes: 1, idle_minutes: 20}}`.

### Storage and credentials
- `StorageGrant(url, access, credentials, endpoint, region, expires_at)`; the URL scheme picks the backend: `file`, `s3`, `gs`, or `http(s)` for the storage proxy. `object_store(grant)` / `zarr_store(grant)` with refresh via heartbeat (for future temporary credentials).
- Jobs carry `grants`: paths under project storage with `r` or `rw`. At claim the broker turns each into a `StorageGrant`. Default (`storage.worker_access = "proxy"`, and always for remote and burst workers): `https://<server as the worker reached it>/api/worker/v1/jobs/<job>/storage/<n>`, authenticated by the job's lease token, so a worker reaches only its job's paths and only while it holds the lease. `"direct"` gives local workers the server's own credentials (only for workers as trusted as the server that can reach the storage, for example a shared disk). AWS STS session policies and GCS downscoped tokens come with the cloud deploys (M3).
- The proxy speaks what obstore's `HTTPStore` sends: GET with Range (offset, suffix, and closed ranges, for shard indexes), HEAD, single-request PUT (streamed to storage, 4 GB cap; the HTTP store has no multipart, so `zarr_store` and `put_bytes` force single PUTs), DELETE, and WebDAV PROPFIND (hrefs are keys relative to the grant). It checks the lease in its own short session and holds no database connection while bytes stream; a PUT checks the lease again once its body has arrived and share-locks the job until the object is stored, and a DELETE holds the same lock while it runs. Completing the job needs a stronger lock, so it waits for mutations in flight, and none can land afterwards: a lost lease aborts the upload before it becomes visible (tested on local disk and S3). The grant root itself is not an object. Caddy allows 4 GiB bodies on the proxy paths only, 8 MiB elsewhere, on both the public site and the worker port.
- Commit: a job that produces an artifact writes `_MANIFEST.json` last. When it reports success, `artifacts.commit_outputs` runs in the same transaction before the job is marked succeeded: no manifest → the attempt fails (retryable); the server lists the files to measure them (its own measurement is what counts), reserves that much of the owner's storage quota (over quota → the job fails for good), marks the artifact committed, and moves its head slot (the previous head becomes superseded).
- Housekeeper GC is the lifecycle mechanism (#1): staging artifacts whose producing job finished without committing them (or with no job, after 48 h) fail; failed ones are deleted after `keep_failed_hours` (48), superseded ones after `keep_superseded_days` (7; replaced proposals after 48 h), expired caches when they expire, and everything in a deleted project. GC never deletes a current head or a prediction that labels were accepted from (a model-verified label op names it; live or undone, since a redo brings it back) unless its project was deleted, or files a waiting or running job has a grant for: it locks the artifact, re-checks in a fresh statement, and marks it `deleting` (releasing its quota and any head) before deleting files, then marks it `deleted`; `enqueue` share-locks the artifacts it grants and refuses ones being deleted, and accepting share-locks the prediction it reads until its op commits, so neither can pass GC. A failed deletion is retried on the next pass and doesn't stop the others, and each housekeeper task runs on its own. Cloud lifecycle rules are only a backstop.
- `ml4paleo-server check-workers` (and the admin `noop` job with `check_storage`) round-trips a scratch object through the worker's storage access; the compose smoke test runs it.

### Security (nothing is public without strong authentication)
`__Host-` session cookie (HttpOnly, Secure, SameSite=Lax), CSRF header + Origin check, every project route through one membership dependency (404 for non-members), route-matrix test over `app.routes`, password length ≥12 + offline common-password list, dummy-hash timing, rate limits (login, signup, reset, v1 claim, usernames tried when adding collaborators), bootstrap admin with random password printed once + forced change + TOTP, no API CORS (Neuroglancer self-hosted same-origin), strict CSP, no third-party scripts or analytics, Caddy body cap 8 MB on `/api` (uploads go direct to S3; the worker storage proxy allows 4 GB), untrusted files parsed only in non-root workers with Pillow/zip limits, secrets via `*_FILE`, TOTP/OIDC secrets encrypted with a data key.

## Risks to watch
- Viewer bandwidth through the proxy (step 14 spike decides 32³ vs 64³ inner chunks for levels 0–1).
- Label writer correctness under concurrent edits and selective undo (property tests).
- TS/Python coordinate conventions (shared golden fixtures).
- Open signup + compute abuse: storage quota + trained-model quota; burst nodes run only `scale_trigger` jobs; admin can disable users and switch to invite-only.
- v1 claim enumeration (24-bit IDs, previously leakable): accepted; claims rate-limited per account and per address, with a lower limit on misses, all claims stopped for the hour once misses from dozens of addresses add up, and admins give a job to the account it belongs to.
- SeaweedFS has no prefix-scoped temp credentials → remote/burst workers use proxy mode; recommend a cloud bucket when remote compute is heavy.
- `weed server` serves its master, filer, and volume ports without authentication. Compose keeps Postgres and SeaweedFS on an internal `private` network that only the server processes join (CI checks this), and workers never join it. Step 9 must give local workers storage access without that network: proxy mode through the API, or SeaweedFS JWT signing.
- nnU-Net on small sparse crops (patch size vs crop size), interactive latency to remote GPUs (M2/M3).
- FIFO lets one large pipeline delay others; tiers mitigate, and fair-share can be added as a config switch later.
- Unverified details to pin with integration tests: zarr 3 partial-shard behaviour, obstore + GCS S3 API, SkyPilot secrets and Postgres state config.
