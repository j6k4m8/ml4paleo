# ml4paleo v2: architecture and build plan

## Context

v1 (`webapp/` Flask + three polling runner scripts + `volume/jobs.json`, plus the `ml4paleo/` library) works for one user on one box. A code review and the open issues show structural limits: no auth, heavy work in HTTP requests on one sync worker, a JSON file as the job store, stuck jobs after crashes, a random-forest-only model with no ignore label, an annotator that serves random 512² patches with no provenance or undo, and local-disk-only storage. v2 is a ground-up re-architecture on branch `v2` (created from `master` at `e97ceab`, after #74–#76 merged). Goals: accounts and sharing, one annotation app (brush, polygon, auto-annotation) with provenance that scales from small training cubes to hand-annotating a whole volume, swappable neural-net segmentation, a real job system that can offload to other machines or the cloud, and storage that works on local disk, S3, or GCS.

| Database | Postgres only: app data, op log, and the job queue. No Redis. Alembic migrations. |

| Quotas | User-facing limits are plain: **storage** (default 10 GB) and **trained models** (count of models a user keeps; deleting one frees a slot). Every dimension (also optional CPU-hours, GPU-hours) is independently configurable per deploy; unset = unlimited. Unlimited projects within quota. "Request more" button → short form → email (or admin inbox when no SMTP). |
| Scheduling | FIFO within a priority tier (interactive > normal > background). Resources, not quotas, limit concurrency. ## Architecture

### Core invariants
1. **Projects have no status enum.** State is derived from committed artifact heads and active pipelines, so the web app and workers can never overwrite each other's status (in v1, saving an annotation could cancel a queued training run, and a retrain could hide finished downloads).
2. **Committed artifacts are immutable.** Each lives at `projects/<pid>/artifacts/<aid>/`; "current" is a DB pointer (`artifact_heads`). Commit is one DB transaction after the worker writes `_MANIFEST.json` last. Partial outputs never become "latest"; export caches keyed by source artifact can't go stale (v1 could cache a partial segmentation zip forever).
3. **One axis boundary.** Storage is `c,z,y,x`. The only XYZ↔ZYX transpose is in `ml4paleo/ome.py`, covered by golden tests (v1 shipped both a transposed PNG export and mirrored meshes).
4. **Heavy work never runs in a request.** The API only enqueues, streams bytes, or applies small label ops.

Library extras keep the server light: the base install (numpy, zarr≥3, obstore, pydantic, pillow, zstandard) is all the API server gets; `[dicom]`, `[rf]`, `[mesh]`, and later `[torch]` are for workers, and `[v1]` holds the old Flask app's dependencies until it is deleted. `requirements.txt`, intern, and the `numcodecs<0.16` pin are gone.

Reused from v1: `_extract_zip_archive`, `_should_ignore_source_file`, `_get_volume_provider` (`webapp/conversionrunner.py`) → `handlers/ingest.py`; `DicomVolumeProvider` spacing logic; `ChunkedMesher` axis/winding fix and `mesh_info.json` (`ml4paleo/meshing/__init__.py`); `_default_features_func` (`ml4paleo/segmentation/rf.py`); `_foreground_metrics` (`webapp/segmentrunner.py`) for per-class metrics; `normalize_annotation_volume` windowing (without the 8-bit cast); v1 sample metadata helpers `get_annotation_pairs`, `load_annotation_sample_metadata`, `annotation_sample_metadata_for_z` (`webapp/apputils.py`) for the importer; bossypaints' viewport loader (`ImageCache.ts`, `getViewportChunkWindow`, `getVisibleChunksForWindow`, progressive levels, `cancelRequestsExcept`) and propagation registry (`server/bossypaints/propagation.py`), both Apache-2.0.

### Data model (Postgres, UUIDv7 keys)
- Identity: `users` (status, is_admin, quota_override jsonb), `sessions` (hashed token), `oidc_providers`, `oidc_identities`, `auth_tokens` (verify/reset/invite), `rate_limits` (unlogged), `site_settings`, `quota_requests`.
- Projects: `projects` (owner, `v1_job_id` unique), `project_members`, `volumes` (shape_czyx, dtype, voxel_size_zyx), `channels` (window), `label_sets`, `label_classes` (0 = unlabeled, 1 = background, 2–254 classes, never reused).
- Labels: `label_chunk(layer, cz, cy, cx, version, class_sha, source_sha, n_labeled, class_counts)`, `op(op_id, op_seq, user/worker, client_op_id, kind, source, tool_params, model_id, job_id, bbox, reverts, conflicts)`, `op_chunk(op_id, chunk, base_version, new_version, new_sha, claim)`, `roi(bbox, kind, status open|complete|skipped, split train|val, origin, score)`, `roi_suggestion`, `training_set(id = sha256 manifest)`, `model` (plugin, version, params, training_set_id, parent, class_map, metrics, artifact).
- Artifacts: `artifacts(kind, state staging|committed|superseded|failed|deleted, bytes, inputs, manifest, produced_by_job, head_slot, cache_key, expires_at, state_changed_at)` (files at `projects/<pid>/artifacts/<aid>/`, derived from the ids), `artifact_heads(project_id, slot, artifact_id)`, `jobs.grants` (`[{path, access}]` under `projects/`), `uploads` (S3 multipart, step 10).
- Queue: `jobs(root_id, parent_id, kind, tier, status blocked|queued|leased|succeeded|failed|cancelled, payload, required_labels[], min_vram_gb, weight, attempts, lease_worker_id, lease_token, lease_expires_at, progress, idempotency_key, scale_trigger bool)`, `job_deps`, `job_attempts`, `workers(token_hash, pool local|remote|burst, labels[], vram_gb, slots, status, last_seen)`, `burst_nodes`.
- Accounting: `usage_ledger`, `user_usage(storage_bytes, trained_models)`, `audit_log`, `v1_claims`, `email_outbox`.

### Worker protocol (`/api/worker/v1`, `Bearer m4pw_<random>`, server stores sha256)
`POST /hello` · `POST /claim` (long-poll ≤25 s, woken by LISTEN/NOTIFY with a 5 s poll as backup; returns job + StorageGrants) · `POST /jobs/{id}/heartbeat` (30 s; 120 s lease; carries progress; returns cancel flag, refreshed grants) · `POST /jobs/{id}/complete` (idempotent) · `POST /jobs/{id}/fail` (`retryable` or not) · `POST /jobs/{id}/release` (a stopping worker hands a job back without using an attempt) · proxy object endpoints for workers without direct storage credentials (step 9). Messages live in `ml4paleo/protocol.py`, shared by server and worker. Every claim carries the worker's caps (kinds, labels, VRAM), so processes that share a token (replicas, or the CPU and GPU workers on one box) can differ; the worker row keeps the last caps seen, and "online" is derived from `last_seen_at`. Every state change is conditional on the lease token (stored hashed); stale leases get 409 and discard output. The housekeeper reaper requeues expired leases with backoff (30 s doubling, max 3 attempts), then fails the job and cancels the rest of its pipeline; it also queues any blocked job whose dependencies all succeeded, as a safety net. Claim query: `FOR UPDATE SKIP LOCKED`, filtered by `kind = ANY(caps.kinds)`, `required_labels <@ caps.labels`, and VRAM, ordered by tier then pipeline submission time (FIFO). Dependencies stay within one pipeline. When parents finish together, each locks the waiting children before checking them, so the last parent to commit always releases the child. A pipeline is cancelled by setting its root job's flag: `cancel_pipeline` waits only for the root row and skips busy rows, and claims, reports, heartbeats, and the reaper all honor the root's flag, so nothing slips through. Locks follow one order (the job, then its pipeline root, then waiting children; workers last) and use `FOR NO KEY UPDATE`, which foreign-key checks don't block. `enqueue` re-reads dependencies under a share lock. Admin API: worker tokens (`/api/admin/workers`), the job list, cancel, and a `noop` diagnostic job; `ml4paleo-server check-workers` runs one from the command line.

### Pipelines (DAG in `jobs` + `job_deps`, progress = Σ weight·progress over `root_id`, SSE to the browser)
- **Upload:** S3 multipart straight from the browser (`/api/projects/<id>/uploads`): the declared size is reserved against the owner's quota at start; the API presigns part URLs (1 h, path-style, signing the part's exact `Content-Length`, so storage refuses a wrong-sized part); to resume, the browser asks which parts storage has (upload id in IndexedDB) and sends the rest; the API completes only when every part is stored with the expected size (64 MiB parts, more for files over 625 GiB; 5 TiB max). Completion commits a `completing` state before asking storage to assemble the parts, so a retry after a crash at any point converges (an assembled file of the right size is accepted; parts still there are assembled), and cleanup of an abandoned `completing` upload both aborts the multipart upload and deletes any assembled file. Unfinished uploads are aborted after 7 days and finished ones deleted after 30 unless a job uses them; jobs can only be given finished uploads. Needs S3-compatible storage (501 on `file://`). On a single box Caddy passes only signed part PUTs (`/ml4paleo/projects/*` with `uploadId`, `partNumber`, `X-Amz-Signature`, and no copy headers) to SeaweedFS on the app's own origin, so no CORS, and strips every `x-amz-*` request header, since the signature covers only the host and length (an unsigned `x-amz-copy-source` would turn a part upload into a copy of another project's file). The compose smoke test uploads a real file this way and checks that a short part is refused and that a copy attempt never reaches storage.
- **Ingest:** `POST /api/projects/<id>/ingest {upload_id}` (a finished upload: one zip of 2D image slices, ordered by name with numbers compared as numbers, or of a DICOM series, ordered along the slice normal) creates the image artifact (staging, head slot `image`) and `ingest.probe`. Archives are read in place through range requests (`open_object`, a seekable buffered reader over the storage grant), member by member, so nothing downloads or unpacks the whole file. Archive guards: the entry count is read from the end-of-directory record (ZIP64 too) before the directory itself, and more than 200k entries are refused; unsafe member names refused (even skipped ones); only stored and deflate members (Python doesn't bound bzip2/LZMA output) and no encrypted ones; total expansion over 1000× refused; members are read in 1 MiB chunks, so deflate output stays within the declared size (a member that claims less than it holds fails as damaged). Each job has a memory budget (the worker's memory, from its container's cgroup limit when it has one, times 0.75, shared among its slots), and a slice's archive member and its decoded pixels may each take a quarter of it (64 MiB to 2 GiB), checked from the image or DICOM header before decoding; compose caps the workers' memory (`M4P_CPU_WORKER_MEMORY`, default 4g) as the last line. A single multi-frame DICOM works too. Damaged archives, bad slices, and malformed probe results (checked before the success is recorded) fail for good. The probe creates the empty OME-Zarr image and writes the slice order to `ingest/source.json`; when it succeeds, the server (`pipelines.after_success`, in the same transaction as the success) adds one `ingest.slab` per shard-deep slab (parallel), one `pyramid.level` per level, and `artifact.finalize`, which records a histogram and default window (0.5–99.5th percentiles of the coarsest level), removes the index, and writes the manifest; its success commits the artifact as the project's image (`GET /api/projects/<id>/image`). Problems with the upload are permanent failures whose first line is shown to the user. Pipelines: `GET /api/projects/<id>/pipelines[/<id>]`, `…/cancel`, and `…/events` (server-sent `status` events, at most once a second, ending when the pipeline finishes or the viewer's sign-in or membership ends; 204 for a pipeline that has already finished, which stops EventSource reconnecting). Staging artifacts that a waiting or running job has a grant for are never abandoned. The compose smoke test ingests a small stack with the real worker.
- **Train + predict:** `training_set` manifest (REPEATABLE READ snapshot: image id, label `op_seq`, ROIs, free labeled regions, chunk shas) → `train` (plugin caps choose CPU/GPU) → `predict.shard` fan-out (512³ shards + halo, outputs classes + uncertainty + 64³ uncertainty grid) → pyramid → finalize → `suggest_rois`. `predict.region` (ROI-scoped, high tier) feeds the proposal overlay.
- **Final segmentation:** `compose_final` per shard = prediction → per-class dust removal (`cc_block` → `cc_merge` union-find → `cc_apply`) → human-label override (`where(label≠0, label, pred)`, complete-ROI unlabeled = background).
- **Mesh:** `mesh.block` (1-voxel overlap; downsample mode/max/gaussian, #22/#24) → `mesh.merge` per class (STL/OBJ/GLB + Neuroglancer precomputed).
- **Export:** zarr-zip, TIFF/PNG stack (in upload orientation), mesh bundle; cached by `(source_aid, fmt, params)`, 7-day expiry, presigned GET.
- **v1 import:** single job on a worker labelled `v1-volume` (v1 volume mounted read-only).

### Label edit path
- Client rasterizes every committed action into per-chunk bit-packed mask deltas (geometry kept in `tool_params` for audit); one op = one stroke/polygon/fill/accept. Ops queue in IndexedDB, flush within 250 ms, retried idempotently by `client_op_id`. Status chip: Saved / Saving n / Offline n.
- Server writer (one transaction per op): idempotency check → lock chunk rows in sorted order → rebase on stale `base_version` (strict ops 409 on overlap; brush ops last-writer-wins per voxel) → write new content-addressed blobs `labels/{layer}/blobs/{sha}` → log `op` + `op_chunk` → NOTIFY (collaborators refetch via ETag) → coalesced `label_pyramid` job.
- Each applied delta records a **claim**: the voxels the op actually wrote (after `only_if`) and the values it wrote there. A chunk's labels are always the overlay of every live op's claim in op order (each voxel takes the value of the last live claim covering it, else unlabeled). Undo and redo are new ops (`reverts=op_id`) that flip an op between live and undone and recompute only that op's voxels from the remaining live claims, so the result never depends on the order of undos and never disturbs voxels a later op also wrote. A property test checks that incremental state always equals a full overlay. Workers (propagation, interactive, imports) submit ops through the same writer with a worker token.
- Everything decoded from a client (masks, values) is decompressed with a hard output limit equal to what its box allows. Label chunks are fixed at 64³ uint8 (sparse and highly compressible); the step 14 viewer spike only decides image chunk sizes.
- Built (step 13): tables `label_classes` (2–254, values never reused, retired with `deleted_at`), `label_chunks` (version, class and source blob hashes, labeled-voxel counts per class), `label_ops` (`seq`, `client_op_id` unique per project, kind edit/undo/redo, `live`, tool, bbox, target), `label_op_chunks` (versions before/after and, for edits, the claim box/mask/values), `rois`. API under `/api/projects/<id>/labels`: classes; `POST ops` (base64 masks; values must be 0, 1, or a live class; one delta per chunk, up to 512; `strict` refuses with the changed chunks); `ops/<seq>/undo|redo` (409 if already in that state); `ops` history; `changes?after=` and `events?after=` (SSE `change` events, while the viewer stays signed in and a member; a reconnect resumes after `Last-Event-ID`) — ops take their `seq` under a per-project lock held until commit, so seqs commit in order and paging by seq never skips one, and a retry that races its first attempt waits for it and gets its result; and `zarr/` — a zarr group with `class` and `source` uint8 arrays shaped like the image in 64³ chunks, served from the current blob with `ETag` = content hash, `If-None-Match` → 304, `X-Chunk-Version` (the next edit's `base_version`), and 404 for all-zero chunks. ROIs under `/api/projects/<id>/rois` (cube or one-voxel slice inside the image; status open/complete/skipped; split train/val). Blobs live at `projects/<id>/labels/blobs/`; reading needs a project image (409 before ingest). Still to come: the coalesced label-pyramid job and garbage collection of unreferenced blobs.
- The data gateway (`GET|HEAD /api/projects/<id>/artifacts/<artifact>/zarr/<key>`) serves committed (or superseded, not yet deleted) artifacts to project members on the same origin, with Range (offset, suffix, closed) and `Cache-Control: private, max-age=31536000, immutable`; missing chunks are 404, which zarr reads as empty. It checks the session and membership, then gives back its database connection before streaming. `GET /api/projects/<id>/image` returns the image's `zarr_url` and, when the server has Neuroglancer, a `neuroglancer_url` (a `zarr3://` layer with the image's display window). The virtual label zarr (`…/labels/…` → current blob, ETag = sha) comes with the label writer (step 13). Optional presigned image reads for cloud deploys come later; labels are always proxied.
- Neuroglancer is built from a pinned release (v2.41.2, commit `e13f1f4`) in a Node stage of the server image and served at `/neuroglancer/` from `M4P_NEUROGLANCER_DIR`, with its own content security policy (`'unsafe-eval'`, because its chunk-decoding worker builds functions at run time and can't start without it; `'wasm-unsafe-eval'` for its WebAssembly decoders; inline styles) that still runs only same-origin scripts (no inline scripts) and connects only to this origin, so a crafted view link can't load or send data elsewhere; it applies only when the build is mounted. Signing out sends `Clear-Site-Data: "cache"`, so cached image chunks don't outlive the session. The compose smoke test reads the ingested image through the gateway and loads Neuroglancer.
- Built (step 14): the web app in `web/` — SvelteKit 3 / Svelte 5 / TypeScript, built by `adapter-static` to an SPA (`index.html` fallback, `ssr = false`) in a Node stage of the server image and served from `M4P_WEB_DIR`. The server's content security policy allows SvelteKit's inline start script by its SHA-256 (read from `index.html` at startup) and inline styles; nothing else inline, and no eval or WebAssembly (the decode workers read zstd with fzstd, in plain JavaScript, because numcodecs.js's zstd builds functions at run time). Routes: sign in (with two-factor codes), sign up, account (forced password change and admin two-factor setup), projects, a project overview (resumable upload → ingest, pipeline progress over SSE, links to the annotator and Neuroglancer), and `/p/<id>/annotate`. The viewer core in `web/src/lib/viewer/`: `tiles.ts` picks the coarsest level whose voxels cover about a screen pixel and the 64² tiles a z plane needs (plus one tile of padding, nearest the center first); `chunks.ts` is a byte-budgeted LRU of decoded 64³ chunks that loads each chunk once, runs a few loads at a time, cancels loads that leave the view, and pins chunks; `decode.worker.ts` + `loader.ts` fetch and decode chunks with zarrita over the data gateway in a pool of module workers and transfer the voxels back; `plane.ts` draws the plane with WebGL2, one `R32F` texture per tile windowed on the GPU (16-bit and float images keep their range), the coarsest level under the chosen one so something shows at once. Pan by dragging, zoom with the wheel around the cursor, step slices with the arrow keys (Shift for 10). CI builds, type-checks (`svelte-check`), and unit-tests the app, and the compose smoke test loads it. Still to come: the 50 GB+ volume spike that settles chunk size and proxy throughput, tri-planar views (step 15), and editing (step 16).
- Built (step 15): the annotator shows XY, YZ, and XZ views laid out 2 × 2 (rows share y, columns share x) with an info panel, or one view at a time (`l` cycles). All views center on one crosshair position and share a zoom; voxels keep their physical shape (`voxel_size_zyx`). The crosshair lines and view borders are colored by axis (x red, y green, z blue). Wheel steps slices, Ctrl/⌘ + wheel or pinch zooms around the cursor, drag pans, and click moves the crosshair. One keymap table (`keymap.ts`) drives the key handlers and the `?` overlay. The label overlay reads the label zarr's `class` array in the same decode workers (a second chunk cache), colors it from the project's classes through a 256-entry palette texture with an opacity slider (#51), and refetches chunks named by `labels/events` as anyone edits them (ETag revalidation makes unchanged chunks a 304). Opacity, label visibility, and layout persist in the browser; zoom and position don't (#37). Labels are full resolution only until the label pyramid exists, so views needing more than 256 label chunks ask you to zoom in.
- Built (step 16, editing): brush, eraser, and polygon tools on any view (`b`, `e`, `p`; `n` or Esc to navigate), a class picker (`1`–`9`), brush radius (`[`, `]`; physical, so thick voxels get a flattened brush), and "paint only unlabeled voxels" (`only_if: unlabeled`). Each stroke or polygon becomes one op: `web/src/lib/labels/raster.ts` rasterizes it on the plane (voxel centers, clipped to the image) and `deltas.ts` splits it into per-chunk deltas exactly as `ml4paleo.labels.deltas` does (checked against the shared fixtures; masks are bit-packed little-endian in zstd frames of raw and run-length blocks, which any zstd decoder reads and which never exceed the server's bounds). Polygons are strict when the page knows every touched chunk's version (the decode worker reports `X-Chunk-Version`), so a conflicting edit is refused and redrawn rather than overwritten; Alt+Enter erases the active class inside a polygon. `OpQueue` sends ops one at a time in order, retries network and server errors with backoff under the same `client_op_id`, keeps unsent edits in IndexedDB across reloads, splits edits over 512 chunks into several ops that undo together, and drives Undo/Redo (Ctrl/⌘+Z, Ctrl/⌘+Shift+Z or Ctrl+Y) for this page's own edits by seq. Edits show at once: deltas apply to the cached label chunks, which stay pinned (and get the deltas re-applied after any reload) until the server answers; a refused edit refetches its chunks. Chunks named by `labels/events` reload in the background, so the screen never blanks. The panel shows Saved / Saving n / Offline · n waiting.
- Built (step 16, ROIs): the ROI tool (`r`) draws a rectangle on any view and makes a one-voxel slice ROI there, or a cube that many voxels deep (centered on the slice and kept inside the image). ROIs show as outlines in every view their box crosses (open dashed amber, complete solid green, skipped gray). The annotator lists them with their status; `g` goes to the next open ROI (centered and fitted, switching a single-view layout to a slice ROI's plane), `c` marks the selected one complete (Shift + `c` reopens), and `/annotate?roi=<id>` opens on one. `/p/<id>/rois` is the gallery (#60): a card per ROI with a thumbnail (the ROI's middle slice from the pyramid level nearest 96 voxels across, with labels when the ROI is at most 256 voxels across), filters by status, status and train/validation split controls, and delete (labels stay).
- Built (step 17, plugins): `ml4paleo.segmentation.plugin` defines `SegmentationPlugin` (name, version, `PluginCaps`, a pydantic `Params` model, `train(data, params, out, ctx) -> TrainResult`, `load(dir) -> Predictor` with `predict_block` over a block padded by the predictor's `halo`) and a registry; plugin modules import scikit-learn or torch only inside their functions, so the API server can list plugins and validate parameters without them. `ml4paleo.segmentation.dataset.TrainingSet` turns an image, label chunks (`BlobLabels` reads them by content hash, so a manifest pins them), and ROIs into crops in the plugin label space: open and complete ROIs tiled to at most `tile`³ (96 by default, or sized to the job's memory from the plugin's `crop_cost`) (unlabeled voxels are background inside complete ROIs of the crop's split, ignored elsewhere; each ROI's train/val split carries over; training crops ignore voxels inside validation ROIs, and a voxel in several ROIs of one split counts once), plus labeled chunks outside those ROIs (tiled the same way) for training only, so validation labels never leak into training. Images are normalized by the display window. The random-forest plugin (`rf`) uses 3D multiscale intensity/edge/texture features (σ 1 to `sigma_max`, halo round(4·σ) + 2: the Gaussian's cutoff plus the gradients), samples up to `samples_per_class` voxels per class by reservoir sampling across all crops (fewer when they and the forest would not fit in half the job's memory) (replacing v1's 1-in-500 negative stride), and scores per-class Dice and IoU on validation crops only (`ml4paleo.segmentation.metrics`).
- Built (step 17, training): `POST /api/projects/<id>/models {plugin, params, name}` pins a training set and starts a `model.train` pipeline. The training set (`training_sets`, id = SHA-256 of its manifest) is read in one REPEATABLE READ snapshot: the image artifact, the live class values, open and complete ROIs (bbox cut to the current image, status, split), and every labeled chunk by content hash; its manifest goes to `projects/<id>/training/<id>/manifest.json`, so the same labels and ROIs give the same training set and later edits never change what a model trained on. The job's grants are the image (read), the label root (read, for blobs), the training set (read), and a staging `model` artifact (write); the worker (which now installs the `rf` extra) builds a `TrainingSet`, runs the plugin, copies its files into the artifact, and writes the manifest last, so success commits it. `models` rows keep plugin, params, class values, metrics, the job, and the artifact; status is derived (training → ready when the artifact commits, failed when the job fails). Training checks for a free trained-model slot before pinning the training set, so a refused training stores nothing. Each model holds one of the project owner's slots from the start of training; failed trainings give theirs back (checked when listing a project's models, and across all of the owner's projects when starting a training), and `DELETE` frees it, cancels a running training, and expires the artifact for garbage collection; deleting the project frees all of its models' slots and cancels its trainings. `GET /api/plugins` lists plugins with their parameter JSON schemas. The web app's `/p/<id>/models` page trains models (with the plugin's settings), follows training over SSE, shows per-class validation Dice/IoU by class name, the quota, and deletes models.
- Built (step 18, prediction): `POST /api/projects/<id>/models/<model>/predict` runs a ready model over the current image as `predict.prepare` → one `predict.shard` per 512³ shard (parallel across workers) → `prediction.finalize`, into a `prediction` artifact that becomes the project's "prediction" head on success. Starting one cancels the project's other predictions still running, so an older one can't finish later and replace it; the same model on the same image while one runs gets 409. The image is normalized with the window the model trained with (kept in its manifest; the image's for models without one), recorded in the prediction's inputs and manifest, and shard jobs ask for the plugin's GPU memory. A prediction is a zarr group in the image grid with `class` (stored label values; 0 where nothing was predicted) and `uncertainty` (255 × (1 − top probability)), uint8 in 64³ chunks inside 512³ shards; each shard job predicts its shard in blocks sized to its memory budget and the image's channels, reading each block with the predictor's halo straight from the image (edge voxels repeated at the image's border), and writes the shard's outputs once when they fit in the budget, or each block's as it goes when they don't (`ml4paleo.segmentation.predict`). Workers keep the last loaded model between shards. `GET /api/projects/<id>/prediction` gives its `zarr_url` (through the data gateway), model, and shape, and is 404 once the image it was made from is replaced. The annotator draws it under the labels with the label palette (background stays clear), with its own toggle (`m`) and opacity, and skips one whose shape doesn't match the image; the models page has a Predict button and shows each model's running or failed prediction (from the pipelines, which carry their `model_id`). Deleting a model cancels its running predictions. Accepting it: with an ROI selected, "Accept prediction here" (`a`) reads the prediction inside the ROI (up to 256³ voxels) and sends one op per predicted value to `POST /api/projects/<id>/labels/accept {client_op_id, prediction_artifact_id, roi_id, deltas}`. The server decides provenance: each delta must write one predicted value (not 0) into only unlabeled voxels inside the ROI, and the stored prediction must hold that value at every voxel the delta selects; then it applies the op as `Source.MODEL_VERIFIED` with the prediction, model, and ROI in its tool record. Plain `POST ops` edits are always `Source.HUMAN` and refuse unknown fields. Accepted ops undo and redo together like any edit, and the op queue now splits edits by size as well as by chunk count to stay under the 8 MiB request limit. Still to come: ROI-scoped proposals computed on demand (`predict.region`), `compose_final`, meshing, and exports.
- Built (step 18, final segmentation): `POST /api/projects/<id>/segmentation {min_voxels}` composes the current prediction into a "segmentation" head: `compose.prepare` → `cc.block` per shard → `cc.merge` → `cc.apply` per shard → `compose.finalize` (`ml4paleo.segmentation.compose`). Each voxel takes its label if anyone labeled it (including accepted predictions), else background inside a complete ROI, else the prediction; then each class's 6-connected pieces smaller than `min_voxels` become background unless someone labeled part of them. Pieces are counted across shards: `cc.block` decides the pieces that touch no seam (a face shared with another shard) itself, and passes on only the seam pieces, numbered compactly, with their sizes capped at `min_voxels` (a labeled piece counts as `min_voxels`), their classes, and their numbers on the seams; `cc.merge` reads those summaries one at a time and joins same-class seam pieces touching across seams as connected components of a sparse graph (scipy) with one edge per pair of pieces, so its memory follows the seams rather than the number of specks; `cc.apply` relabels (labeling is deterministic) and writes the shard. A shard job holds the shard and one int32 array of piece ids, reused for each class, and counts by z slabs sized from its memory budget; every step works out what it needs first and fails for good with a clear message rather than go over its budget. Labels and complete ROIs are pinned at start (chunk hashes, carried in `compose.prepare`'s payload, which writes them into the artifact as `inputs.json`, so a start that never commits leaves no files), so later edits don't change the result; per-shard scratch files (compressed `.npz`) are deleted at the end, and the scratch of a failed or cancelled run goes later, when garbage collection removes its failed artifact. A project makes one at a time (409 with the running pipeline's id), and only from a prediction of its current image. `GET /api/projects/<id>/segmentation` describes it from what the server recorded at start (model, `min_voxels`, and `labels_as_of`, when the newest included label edit was made); the annotator shows it as a layer, and the new Results page makes it and follows the newest one from the project's pipelines, so it survives a reload.
- Built (step 18, meshes): `POST /api/projects/<id>/meshes {downsample 1|2|4|8, method any|majority, simplify}` meshes the final segmentation into a "meshes" head: one `mesh.block` per 256³ block → a `noop` that waits for them all (so joins depend on one job, not every block) → one `mesh.join` per class → `mesh.finalize` (`ml4paleo.meshing.blocks`). Each block reads one extra coarse voxel on its high sides, so neighbouring blocks produce the same vertices on the plane they share, and pads with nothing at the volume's faces, so surfaces there are closed. zmesh takes memory and time in proportion to a surface (a porous block can take gigabytes and minutes) and holds the GIL throughout, so a block counts its class/non-class voxel faces first and meshes in sub-boxes, halved on a power-of-two grid until each fits half the job's memory budget and about 20 s of zmesh; sub-boxes meet the way blocks do, and a block too detailed even in 16³ sub-boxes fails for good, asking for a coarser resolution. Blocks write each class's pieces, seam vertices marked, to `scratch/<block>/<value>.npz` as they go, and a summary to `scratch/<block>.json`. A join streams its class block by block: it welds seam vertices through a dict (dropping each block's once no later block can reach them) and drops triangles that collapse, writes the STL as it goes, spools vertices and triangles to disk for the OBJ and GLB, and uploads from disk (the storage proxy gets a streamed PUT; obstore's HTTP store would hold the file in memory), so its memory doesn't grow with the mesh. A file over the proxy's 4 GiB, or more seam vertices than the budget holds, fails for good, asking for a coarser resolution or more simplification. Each join writes `<value>.json` (triangles, vertices, files) for finalize. Downsampling (#22/#24) keeps a coarse voxel if any of its voxels is the class (thin parts survive) or if most of those inside the scan are (smoother); coarse voxels cut by the scan's far faces end at them. `simplify` bounds how far simplification may move a surface, in voxels at that resolution (0 keeps every triangle); vertices on seams never move, so simplified pieces still join. Meshes are in (x, y, z), scaled by the voxel size of the image the segmentation was predicted from and in its unit (voxels if the scan gave none), as `<value>.stl`, `.obj` (nine significant digits), and `.glb` (the same vertices, with the node scaled to meters, as glTF expects), with `mesh_info.json` (axis order, units, voxel size, options, and per class its name, color, files, and counts). A project makes one set of meshes at a time (409), and not while its owner is out of storage (403). The v1 `ChunkedMesher` moved to `ml4paleo.meshing.chunked`, imported lazily so the package stays importable without the mesh extra. `GET /api/projects/<id>/meshes` gives the info, the source segmentation, and a `files_url` under `/api/projects/<id>/artifacts/<artifact>/files/` (the data gateway, for downloads); the Results page makes meshes, follows running pipelines after a reload, flags meshes made from an older segmentation, and links each class's files, named for the project, the class's value, and its name (letters in any script).

- Plugin label space: background 0, classes 1..K, IGNORE 255 (from unlabeled voxels outside complete ROIs).
- RF: labeled voxels only, balanced per-class sampling (replaces the 1/500 negative stride), 3D features, halo = round(4·σmax) + 2.
- nnU-Net v2: crops as cases, `ignore` label in `dataset.json`, pre-normalized `noNorm` channel with a global window, time-budgeted trainer, warm start from parent model.
- MONAI SegResNet: CE with `ignore_index` + masked Dice, label-balanced patch sampling, sliding-window inference.
- Metrics: per-class Dice/IoU on validation ROIs (20% of non-suggested ROIs once ≥5 exist), not on training data.
- Active learning: score 64³ cells by top-10% entropy (from the uncertainty grid, or sampled crops inside the specimen mask), NMS + diversity, 20% random exploration.

### Scheduling, compute, and burst
- Local workers via compose; `setup.sh` detects `nvidia-smi` and the NVIDIA container runtime and sets `COMPOSE_PROFILES=gpu`. Local workers share one token (`secrets/worker_token`, registered by `migrate`) and reach only the worker API, through an unpublished Caddy port on the `jobs` network.
- Remote workers: admin creates a worker token in `/admin/workers`, runs `docker run ghcr.io/j6k4m8/ml4paleo-worker-gpu --server ... --token-file ...`.
- Scaler (compose profile `burst`, sole holder of cloud credentials, runs the SkyPilot API server with Postgres state): every 30 s, per pool: demand = queued `scale_trigger` jobs whose requirements match the pool and no non-burst worker can take soon → target nodes = clamp(ceil(backlog/30 min), `min_nodes`, `max_nodes`) → `sky.launch` worker clusters (`down=True`, idle autostop, per-node expiring worker token) → reconcile and tear down idle/orphaned/silent nodes. Background-tier jobs set `scale_trigger=false`.
- Pool config example: `pools: {train: {node_type: L4, max_nodes: 2}, predict: {node_type: L4, max_nodes: 4}, interactive: {node_type: A10G, max_nodes: 1, idle_minutes: 20}}`.

### Storage and credentials
- `StorageGrant(url, access, credentials, endpoint, region, expires_at)`; the URL scheme picks the backend: `file`, `s3`, `gs`, or `http(s)` for the storage proxy. `object_store(grant)` / `zarr_store(grant)` with refresh via heartbeat (for future temporary credentials).
- Jobs carry `grants`: paths under project storage with `r` or `rw`. At claim the broker turns each into a `StorageGrant`. Default (`storage.worker_access = "proxy"`, and always for remote and burst workers): `https://<server as the worker reached it>/api/worker/v1/jobs/<job>/storage/<n>`, authenticated by the job's lease token, so a worker reaches only its job's paths and only while it holds the lease. `"direct"` gives local workers the server's own credentials (only for workers as trusted as the server that can reach the storage, for example a shared disk). AWS STS session policies and GCS downscoped tokens come with the cloud deploys (M3).
- The proxy speaks what obstore's `HTTPStore` sends: GET with Range (offset, suffix, and closed ranges, for shard indexes), HEAD, single-request PUT (streamed to storage, 4 GB cap; the HTTP store has no multipart, so `zarr_store` and `put_bytes` force single PUTs), DELETE, and WebDAV PROPFIND (hrefs are keys relative to the grant). It checks the lease in its own short session and holds no database connection while bytes stream; a PUT checks the lease again once its body has arrived and share-locks the job until the object is stored, and a DELETE holds the same lock while it runs. Completing the job needs a stronger lock, so it waits for mutations in flight, and none can land afterwards: a lost lease aborts the upload before it becomes visible (tested on local disk and S3). The grant root itself is not an object. Caddy allows 4 GiB bodies on the proxy paths only, 8 MiB elsewhere, on both the public site and the worker port.
- Commit: a job that produces an artifact writes `_MANIFEST.json` last. When it reports success, `artifacts.commit_outputs` runs in the same transaction before the job is marked succeeded: no manifest → the attempt fails (retryable); the server lists the files to measure them (its own measurement is what counts), reserves that much of the owner's storage quota (over quota → the job fails for good), marks the artifact committed, and moves its head slot (the previous head becomes superseded).
- Housekeeper GC is the lifecycle mechanism (#1): staging artifacts whose producing job finished without committing them (or with no job, after 48 h) fail; failed ones are deleted after `keep_failed_hours` (48), superseded ones after `keep_superseded_days` (7), expired caches when they expire, and everything in a deleted project. GC never deletes a current head (unless its project was deleted) or files a waiting or running job has a grant for: it locks the artifact, re-checks in a fresh statement, and marks it `deleting` (releasing its quota and any head) before deleting files, then marks it `deleted`; `enqueue` share-locks the artifacts it grants and refuses ones being deleted, so the two can't pass each other. A failed deletion is retried on the next pass and doesn't stop the others, and each housekeeper task runs on its own. Cloud lifecycle rules are only a backstop.
- `ml4paleo-server check-workers` (and the admin `noop` job with `check_storage`) round-trips a scratch object through the worker's storage access; the compose smoke test runs it.

### Security (nothing is public without strong authentication)
`__Host-` session cookie (HttpOnly, Secure, SameSite=Lax), CSRF header + Origin check, every project route through one membership dependency (404 for non-members), route-matrix test over `app.routes`, password length ≥12 + offline common-password list, dummy-hash timing, rate limits (login, signup, reset, v1 claim), bootstrap admin with random password printed once + forced change + TOTP, no API CORS (Neuroglancer self-hosted same-origin), strict CSP, no third-party scripts or analytics, Caddy body cap 8 MB on `/api` (uploads go direct to S3; the worker storage proxy allows 4 GB), untrusted files parsed only in non-root workers with Pillow/zip limits, secrets via `*_FILE`, TOTP/OIDC secrets encrypted with a data key.

## Risks to watch
- Viewer bandwidth through the proxy (step 14 spike decides 32³ vs 64³ inner chunks for levels 0–1).
- Label writer correctness under concurrent edits and selective undo (property tests).
- TS/Python coordinate conventions (shared golden fixtures).
- Open signup + compute abuse: storage quota + trained-model quota; burst nodes run only `scale_trigger` jobs; admin can disable users and switch to invite-only.
- v1 claim enumeration (24-bit IDs, previously leakable): accepted; rate limits, claim window, admin reassign.
- SeaweedFS has no prefix-scoped temp credentials → remote/burst workers use proxy mode; recommend a cloud bucket when remote compute is heavy.
- `weed server` serves its master, filer, and volume ports without authentication. Compose keeps Postgres and SeaweedFS on an internal `private` network that only the server processes join (CI checks this), and workers never join it. Step 9 must give local workers storage access without that network: proxy mode through the API, or SeaweedFS JWT signing.
- nnU-Net on small sparse crops (patch size vs crop size), interactive latency to remote GPUs (M2/M3).
- FIFO lets one large pipeline delay others; tiers mitigate, and fair-share can be added as a config switch later.
- Unverified details to pin with integration tests: zarr 3 partial-shard behaviour, obstore + GCS S3 API, SkyPilot secrets and Postgres state config.
